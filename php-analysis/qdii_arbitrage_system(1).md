## 一、估值计算

### 1.1 校准因子计算流程
```
① 获取基准日数据
   ├─ 基金官方净值获取
   │   ├─ 数据源：新浪财经基金API（`http://hq.sinajs.cn/list=f_xxxxxx`）
   │   ├─ 解析逻辑：分割字符串提取净值和日期
   │   └─ 异常处理：网络超时重试3次，数据缺失使用上一次有效数据
   ├─ XOP收盘价获取
   │   ├─ 数据源：Yahoo Finance API
   │   ├─ 参数：`range=1d, interval=1d`
   │   └─ 时区转换：UTC→北京时间（+8小时）
   └─ USDCNY汇率获取
       ├─ 数据源：中国货币网
       ├─ 解析逻辑：遍历records数组提取USD/CNY汇率
       └─ 精度处理：保留4位小数
② 计算因子
   ├─ 公式：`fFactor = (XOP_close × USDCNY_rate) / fund_net_value`
   ├─ 精度处理：保留6位小数
   └─ 边界检查：`0.0001 < factor < 10000`，超出范围使用默认因子1.0
③ 存储与更新
   ├─ 数据库表：`calibration_factors`
   ├─ 存储逻辑：UPSERT语句（存在则更新，不存在则插入）
   └─ 更新触发：基金净值更新后通过Celery异步任务执行
```

### 1.2 净值估算方法
```
① 实时数据获取
   ├─ XOP实时价格
   │   ├─ 数据源：新浪美股API（`http://hq.sinajs.cn/list=us_xop`）
   │   ├─ 更新频率：每30秒
   │   └─ 缓存策略：Redis缓存30秒
   ├─ USDCNY实时汇率
   │   ├─ 数据源：新浪外汇API（`http://hq.sinajs.cn/list=fx_susdcny`）
   │   ├─ 更新频率：每10秒
   │   └─ 缓存策略：Redis缓存10秒
   └─ 校准因子
       ├─ 查询逻辑：数据库获取最新有效因子
       └─ 缓存策略：Redis缓存5分钟
② 计算过程
   ├─ 基础计算：`raw_value = XOP_price × USDCNY_rate`
   ├─ 因子调整：`estimated_nav = raw_value / calibration_factor`
   └─ 精度处理：保留4位小数
③ 数据验证
   ├─ 异常值检测：价格/汇率超出合理范围时使用上一次有效数据
   ├─ 数据完整性检查：缺失数据时尝试备选数据源
   └─ 波动检测：估值波动>10%时使用上一次有效估值
```

### 1.3 仓位调整逻辑
```
① 参数获取
   ├─ 仓位比例
   │   ├─ 数据源：数据库`fund_config`表
   │   ├─ 默认值：0.95
   │   └─ 缓存策略：Redis缓存1小时
   ├─ 估算净值：实时计算结果
   └─ 基期净值：最新官方净值（数据库`funds`表）
② 加权计算
   └─ 公式：`adjusted_value = position_ratio × estimated_value + (1-position_ratio) × base_net_value`
③ 边界处理
   ├─ 仓位范围限制：`0 ≤ position_ratio ≤ 1`，超出范围强制修正
   └─ 异常值过滤：估值为负或波动>10%时使用基期净值
```

### 1.4 溢价率计算
```
① 数据输入
   ├─ 场内交易价格：新浪A股API，每3秒更新
   ├─ 调整后估值：仓位调整结果
   └─ 阈值：数据库`strategy_config`表，默认±0.5%
② 计算逻辑
   ├─ 公式：`premium_rate = (market_price / adjusted_value) - 1`
   └─ 精度处理：保留4位小数
③ 结果判断
   ├─ 溢价信号：`premium_rate > sell_threshold`（持续>30秒）
   ├─ 折价信号：`premium_rate < buy_threshold`（持续>30秒）
   └─ 持有信号：溢价率在阈值范围内
```

## 二、套利策略

### 2.1 信号生成规则
```
① 数据源
   ├─ 实时溢价率：每3秒更新，Redis缓存3秒
   ├─ 阈值配置：支持固定/动态/分位数三种类型
   └─ 历史信号记录：查询最近1小时内的信号用于去重
② 规则判断
   ├─ 卖出信号：溢价率>阈值且持续>30秒，冷却期≥5分钟
   ├─ 买入信号：溢价率<-阈值且持续>30秒，冷却期≥5分钟
   └─ 持有信号：不满足买入或卖出条件
③ 信号去重
   ├─ 冷却期设置：同方向信号间隔≥5分钟，不同方向≥2分钟
   ├─ 去重实现：Redis计数器记录最后发送时间
   └─ 存储策略：立即存入数据库，异步发送通知
```

### 2.2 阈值设定逻辑
```
① 阈值类型
   ├─ 固定阈值：配置文件直接设置，适用稳定市场
   ├─ 动态阈值：基于最近30天波动率计算，适用波动市场
   └─ 分位数阈值：基于历史溢价率分布的分位数，适用统计策略
② 阈值调整
   ├─ 手动调整：管理员通过API配置，需要权限验证
   └─ 自动调整：连续3次信号无收益时自动增加20%阈值
③ 阈值验证
   ├─ 回测验证：最近1年历史数据，评估胜率、收益率、最大回撤
   └─ 实盘验证：使用10%资金测试1个月，达标后扩大比例
```

### 2.3 风险控制机制
```
① 仓位限制
   ├─ 单只基金最大持仓比例：20%（可配置）
   ├─ 总持仓市值限制：10万元（可配置）
   └─ 行业/板块集中度限制：30%（可配置）
② 交易限制
   ├─ 最小交易间隔：5分钟（止损订单和管理员操作除外）
   ├─ 每日最大交易次数：10次（可配置）
   └─ 单笔最大金额：1万元（可配置，超限自动调整）
③ 异常处理
   ├─ 熔断机制：价格波动>5%、连续3次下单失败、数据源异常时触发
   └─ 止损/止盈策略：亏损>2%止损，盈利>3%止盈，盈利回吐>1%跟踪止损
```

## 三、数据来源

### 3.1 新浪财经API解析
```
① 接口类型
   ├─ 基金数据：`http://hq.sinajs.cn/list=f_xxxxxx`
   ├─ 股票数据：`http://hq.sinajs.cn/list=sh/szxxxxxx`
   └─ 外汇数据：`http://hq.sinajs.cn/list=fx_susdcny`
② 数据格式解析
   ├─ 字符串分割：逗号分隔
   ├─ 编码转换：GB2312→UTF-8
   └─ 类型转换：字符串→浮点数
③ 异常处理
   ├─ 接口超时：重试3次，间隔1秒
   ├─ 数据缺失：使用上一次有效数据
   └─ 格式错误：记录日志并使用默认值
```

### 3.2 中国货币网数据获取
```
① 接口地址：`https://www.chinamoney.com.cn/r/cms/www/chinamoney/data/currency/`
② 数据结构
   ├─ 顶层结构：`{"data": {"records": [...], "lastDate": "..."}}`
   └─ records元素：`{"vrtEName": "USD/CNY", "price": "7.2456"}`
③ 获取逻辑
   ├─ 定时获取：每日09:15后执行
   ├─ 数据解析：提取USD/CNY、HKD/CNY等汇率
   └─ 数据库存储：`exchange_rates`表，当日数据已存在则跳过
```

### 3.3 Yahoo Finance数据获取
```
① 接口类型
   ├─ 实时数据：`https://query1.finance.yahoo.com/v7/finance/chart/{symbol}`
   ├─ 历史数据：`https://query1.finance.yahoo.com/v7/finance/download/{symbol}`
   └─ 股票信息：`https://query2.finance.yahoo.com/v1/finance/search`
② 数据解析
   ├─ 实时数据：提取`regularMarketPrice`字段
   ├─ 历史数据：CSV格式，使用pandas读取
   └─ 股票信息：提取`shortName`字段
③ 缓存策略
   ├─ 实时数据：Redis缓存1分钟
   ├─ 历史数据：数据库永久存储
   └─ 缓存键设计：`{symbol}:{data_type}:{date}`
```

### 3.4 数据缓存策略
```
① 缓存类型
   ├─ 实时数据缓存：过期时间1分钟
   ├─ 历史数据缓存：永久存储（定期清理）
   └─ 计算结果缓存：过期时间5分钟
② 缓存策略
   ├─ 过期时间设置：高频数据短过期，低频数据长过期
   ├─ 缓存更新策略：主动更新+被动失效+定时刷新
   └─ 缓存失效处理：降级到数据库查询，熔断时使用默认值
③ 缓存优化
   ├─ 热点数据预加载：开盘前5分钟加载基金列表和最新净值
   ├─ 缓存穿透处理：空数据也缓存，过期时间5分钟
   └─ 缓存一致性保证：数据库更新时清除相关缓存
```

## 四、技术架构

### 4.1 API层设计
```
① 接口分类
   ├─ 基金数据接口：获取基金列表、详情、估值
   ├─ 套利信号接口：获取信号列表、历史记录
   ├─ 消息推送接口：钉钉、Telegram、微信推送
   └─ 系统管理接口：健康检查、配置管理、日志查询
② 接口规范
   ├─ RESTful设计：资源定位使用名词，HTTP方法语义清晰
   ├─ 状态码：200成功、400错误、401未授权、403权限不足、404不存在、500服务器错误
   └─ 错误处理：统一格式`{"error": "...", "code": "..."}`
③ 安全设计
   ├─ API Key认证：请求头`X-API-Key`，数据库验证
   ├─ 请求频率限制：每分钟最多100次，Redis计数器实现
   └─ IP白名单：配置文件或数据库配置，超限返回403
```

### 4.2 业务层设计
```
① 核心服务
   ├─ ValuationService：估值计算，依赖DataCollector和CalibrationRepository
   ├─ StrategyService：套利策略判断，依赖ThresholdRepository和RiskManager
   ├─ SignalService：信号生成与管理，依赖SignalRepository和NotificationService
   └─ NotificationService：消息推送，依赖HTTP客户端
② 服务间通信
   ├─ 同步调用：直接方法调用，适用于需要立即结果的场景
   ├─ 异步消息：Celery任务队列，适用于不需要立即结果的场景
   └─ 事件驱动：Redis Pub/Sub，适用于多服务响应同一事件
③ 事务管理
   ├─ 数据库事务：SQLAlchemy事务上下文，单数据库操作
   ├─ 分布式事务：两阶段提交或补偿事务，跨数据库操作（如需要）
   └─ 补偿机制：记录操作日志，失败时执行反向操作
```

### 4.3 数据层设计
```
① 数据库设计
   ├─ funds表：基金基本信息（代码、名称、类型、跟踪标的）
   ├─ exchange_rates表：汇率数据（货币对、汇率值、日期、数据源）
   ├─ signals表：信号记录（基金ID、类型、溢价率、阈值、状态）
   ├─ trades表：交易日志（信号ID、基金ID、类型、金额、价格、状态）
   └─ calibration_factors表：校准因子（基金ID、因子值、基准日期）
② 数据访问层
   ├─ Repository模式：封装数据库操作，提供CRUD方法
   ├─ ORM使用：SQLAlchemy，减少SQL编写，防止SQL注入
   └─ 查询优化：索引、分页、缓存
③ 数据迁移
   ├─ 数据库版本控制：Alembic，迁移文件存放在`alembic/versions`
   ├─ 数据同步：Celery定时任务，增量同步变化数据
   └─ 数据备份：每日凌晨3点pg_dump备份，本地+云存储
```

### 4.4 基础设施配置
```
① 服务器配置
   ├─ CPU/内存：生产环境4核8G，开发环境2核4G
   ├─ 网络配置：公网IP，开放80/443/6379/5432端口
   └─ 存储配置：SSD硬盘，至少50GB容量
② 容器化部署
   ├─ Docker镜像构建：多阶段构建，优化体积
   ├─ Docker Compose编排：服务隔离，一键部署
   └─ Kubernetes部署（可选）：高可用、自动扩缩容
③ 监控告警
   ├─ 性能监控：Prometheus + Grafana，监控API请求数、延迟、CPU/内存
   ├─ 日志收集：ELK Stack，收集应用/数据库/任务日志
   └─ 异常告警：钉钉/Telegram/邮件，告警级别CRITICAL/WARNING/INFO
```

## 五、代码结构

### 5.1 模块划分
```
① 模块职责
   ├─ api/：对外REST API接口（FastAPI）
   ├─ core/：核心业务逻辑（估值、策略、信号）
   ├─ data/：数据层（采集器、Repository、模型）
   ├─ tasks/：定时任务（Celery）
   └─ utils/：工具函数（HTTP客户端、日志、配置）
② 模块间依赖
   ├─ api → core → data（API调用业务逻辑，业务逻辑调用数据层）
   ├─ tasks → core → data（定时任务调用业务逻辑）
   └─ utils → 各模块（工具函数被所有模块使用）
③ 模块解耦
   ├─ 接口抽象：定义抽象基类，子类实现具体逻辑
   ├─ 依赖注入：通过参数传入依赖，提高可测试性
   └─ 配置化：可变参数放入配置文件，便于调整
```

### 5.2 类设计
```
① 类职责单一
   ├─ ValuationCalculator：仅负责估值计算
   ├─ ArbitrageStrategy：仅负责套利策略判断
   ├─ SinaCollector：仅负责新浪数据采集
   └─ FundRepository：仅负责基金数据访问
② 类关系
   ├─ 继承关系：如`BaseCollector`→`SinaCollector`
   ├─ 组合关系：如`StrategyEngine`包含`ValuationCalculator`
   └─ 依赖关系：如`SignalGenerator`依赖`ArbitrageStrategy`
③ 接口设计
   ├─ 抽象方法：定义接口方法，子类实现
   ├─ 返回类型提示：使用Python类型注解
   └─ 参数验证：使用Pydantic模型
```

### 5.3 函数职责
```
① 函数粒度
   ├─ 单一职责原则：一个函数只做一件事
   ├─ 函数长度限制：不超过50行
   └─ 参数数量限制：不超过5个
② 函数命名
   ├─ 动词+名词格式：如`calculate_premium`、`fetch_fund_data`
   ├─ 清晰命名：避免歧义
   └─ 避免缩写：除非广泛认可
③ 错误处理
   ├─ 异常捕获：try-except块
   ├─ 错误返回：返回错误信息而非直接抛出异常
   └─ 日志记录：记录错误详情用于排查
```

### 5.4 依赖关系
```
① 依赖管理
   ├─ requirements.txt：列出所有依赖
   ├─ 版本锁定：pip freeze生成固定版本
   └─ 虚拟环境：隔离项目依赖
② 依赖注入
   ├─ 构造器注入：通过__init__方法传入依赖
   ├─ 方法注入：通过方法参数传入依赖
   └─ 服务容器：统一管理依赖实例
③ 循环依赖处理
   ├─ 接口解耦：通过抽象接口避免直接依赖
   ├─ 延迟加载：使用时才创建实例
   └─ 依赖倒置：依赖抽象而非具体实现
```
